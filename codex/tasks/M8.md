# Задача для Codex: Реализовать этап M8 — Сигналы

**Спецификация**: см. `README.md`, `./docs/TECH_STYLE_GUIDE.md`,
`./docs/stages/M8_SIGNALS.md`, диаграммы в `./docs/diagrams/**` (sequence + flows),
особенно `m08_signals_generate`.

> В этой задаче **не требуется** рефакторить ранее созданный код под гайд во всём репозитории —
> применяй правила `TECH_STYLE_GUIDE.md` только к новому коду M8.

## Инварианты (из TECH_STYLE_GUIDE)

* Java 25; Spring Boot 3.x; **jOOQ-only** (запрещено добавлять Spring Data JPA).
* Lombok; MapStruct (имплементации генерятся при билде).
* springdoc-openapi-starter-webmvc-ui (Swagger UI); Spring Security (JWT; dev можно упростить).
* Конфиги: `application.yaml` (dev/prod), `docker-compose.yaml` (PostgreSQL). **Без триггеров** в БД.
* Все версии зависимостей — через `<properties>` в `pom.xml`.
* Слои: client/domain/api/persistence. **Маппинг только через domain** (rich‑модель).
* Канонические таймфреймы — в YAML (canonical → per‑exchange mapping); **только закрытые свечи**; UTC.
* Стиль нового кода: одна переменная на строку; `{}` после `if`; аннотации **над** полями; строки → `Constants.*`; конечные значения → `enum`.
* Коды ошибок (dot‑нотация) и исключения: `ServiceException`, `UnexpectedException`.
* Проверки: `Objects.isNull/nonNull`, `Objects.equals`, `BooleanUtils.isFalse`, `CollectionUtils.isEmpty/isNotEmpty`.
* В миграциях — `COMMENT ON TABLE/COLUMN` **на всё**; в persistence‑моделях — **Javadoc на класс и поля**.

## Что реализовать в M8

### 1) Таблицы (SQL‑миграции с полными COMMENT ON)

1. `signal_event`

   * Поля:

     * `id BIGSERIAL PK`
     * `exchange_instrument_id BIGINT NOT NULL` — FK на связку биржа×инструмент
     * `timeframe_canonical TEXT NOT NULL`
     * `ts_utc TIMESTAMP NOT NULL` — метка «решающей» свечи (UTC)
     * `signal_type TEXT NOT NULL` — enum‑подобное значение (например, `EMA_TREND`, `MACD_IMPULSE`, `RSI_REBOUND`, ...)
     * `direction TEXT NOT NULL` — `LONG` | `SHORT` | `NEUTRAL`
     * `score NUMERIC(10,6) NOT NULL` — диапазон `[-1..+1]`
     * `reason JSONB NOT NULL` — структурное объяснение (см. ниже)
     * `signal_params_id BIGINT NOT NULL` — FK на immutable параметры
     * `version INT NOT NULL` — версия правил
     * `created_at TIMESTAMP NOT NULL`
   * Уникальность идемпотентности: `UK(exchange_instrument_id, timeframe_canonical, ts_utc, signal_type, signal_params_id, version)`
2. `signal_checkpoint`

   * Поля:

     * `signal_type TEXT NOT NULL`
     * `timeframe_canonical TEXT NOT NULL`
     * `exchange_instrument_id BIGINT NOT NULL`
     * `signal_params_id BIGINT NOT NULL`
     * `version INT NOT NULL`
     * `last_ts TIMESTAMP NOT NULL`
     * `updated_at TIMESTAMP NOT NULL`
   * Уникальность: `UK(signal_type, timeframe_canonical, exchange_instrument_id, signal_params_id, version)`

> Замечание: таблицы параметров `signal_params` уже существуют (M2). Использовать имиutable‑подход `resolveOrCreate` (см. ниже).

### 2) Конфигурация (`application.yaml`)

```yaml
app:
  signals:
    debounceBars: 2         # минимальный разрыв между однотипными сигналами
    cooldownBars: 5         # bars, в течение которых не выпускаем повторный сигнал того же типа и направления
    htfFilter:
      enabled: true
      htf: "4 hours"       # фильтр старшим таймфреймом для LTF сигналов
    numeric:
      scoreScale: 6
      rounding: HALF_UP
```

### 3) Reason (объяснимость) — структура JSONB

* Тело `reason` — строго структурированное:

```json
{
  "inputs": [
    { "indicator": "EMA", "tf": "1 hour", "fields": { "ema10": "...", "ema20": "..." }, "weight": 0.35, "contrib": 0.21 },
    { "indicator": "MACD", "tf": "15 minutes", "fields": { "hist": "..." }, "weight": 0.45, "contrib": 0.33 }
  ],
  "filters": [
    { "name": "HTF_EMA_TREND", "passed": true, "detail": { "emaSlope": "..." } }
  ],
  "score": 0.54,
  "direction": "LONG",
  "notes": "debounce ok; cooldown ok"
}
```

* Поля `weight`/`contrib` (по желанию) отражают вклад входов в итоговый `score`.

### 4) Сервис: `SignalService`

Реализовать сервис, который **инкрементально** генерирует сигналы по каждой серии `(exchange_instrument × timeframe)`:

* Метод: `generate(exchangeInstrumentId, timeframe, signalType, paramsRef)`

  1. `resolveOrCreate(signal_params)` — поиск/создание immutable записи по канону (type, timeframe, version, canonical_json).
  2. Стартовая точка — `signal_checkpoint` или `coverage_start_utc` (учесть warmup значений индикаторов).
  3. На каждый бар (ASC):

     * загрузить необходимые **значения индикаторов** (EMA/MACD/RSI/Stoch/BB/OBV) на нужных ТФ, не позже `ts`;
     * применить правила для `signalType` (например: EMA trend: `Close>EMA(L)` и `EMA(S)>EMA(L)` ⇒ bull; MACD impulse: `MACD>0 & hist↑` и т.д. — см. M6–M7);
     * применить debounce/cooldown; при включённом `htfFilter.enabled` — фильтр по HTF;
     * посчитать `score ∈ [-1..+1]`, `direction`;
     * собрать `reason` и **вставить** в `signal_event` (идемпотентно `ON CONFLICT DO NOTHING`).
  4. Обновить/вставить `signal_checkpoint(last_ts)`.

* Предусмотреть режим пакетной генерации: `generateRange(exchangeInstrumentId, timeframe, signalType, paramsRef, fromUtc, toUtc)` — для бэктеста/массовой докачки.

### 5) REST‑эндпоинты (Swagger)

* `POST /api/signals/generate` — тело: `{ exchangeInstrumentId, timeframe, signalType, paramsRef }` — запускает инкрементальную генерацию.
* `POST /api/signals/generate-range` — `{ exchangeInstrumentId, timeframe, signalType, paramsRef, fromUtc, toUtc }`.
* `GET  /api/signals/latest` — параметры: `exchangeInstrumentId, timeframe, signalType, limit?` — вернуть последние `N` сигналов.
* `GET  /api/signals/checkpoint` — получить checkpoint для серии.

### 6) Enum/константы

* `SignalType` (enum): `EMA_TREND`, `MACD_IMPULSE`, `RSI_REBOUND`, `STOCH_REVERSAL`, `BB_BREAKOUT`, `OBV_CONFIRM` (можно расширять).
* `Direction` (enum): `LONG`, `SHORT`, `NEUTRAL`.
* Константы кодов ошибок/полей — в `util/Constants`.

### 7) Метрики

* `signals.generated.total{signalType=...}` — количество записанных сигналов.
* `signals.debounce.skip{signalType=...}` — пропуски из‑за debounce.
* `signals.cooldown.skip{signalType=...}` — пропуски из‑за cooldown.
* `signals.checkpoint.updated` — обновления чекпоинта.

## Требования к БД/миграциям

* SQL без триггеров; полные `COMMENT ON TABLE/COLUMN` на все новые сущности.
* Индексы под выборки: `(exchange_instrument_id, timeframe_canonical, ts_utc)` и по `signal_type`.
* Уникальный ключ `signal_event` как указано выше (идемпотентность).
