# Задача для Codex: Реализовать этапы M4–M5

**Спецификация**: см. `README.md`, `./docs/TECH_STYLE_GUIDE.md`,
`./docs/stages/M4_HISTORY_INGESTION.md`, `./docs/stages/M5_DATA_CONSISTENCY.md`,
диаграммы в `./docs/diagrams/**` (sequence + flows).

## Инварианты (из TECH_STYLE_GUIDE)

* Java 25; Spring Boot 3.x; **jOOQ-only** (запрещено добавлять Spring Data JPA).
* Lombok; MapStruct (имплементации генерятся при билде).
* springdoc-openapi-starter-webmvc-ui (Swagger UI); Spring Security (JWT; dev можно упростить).
* Конфиги: `application.yaml` (dev/prod), `docker-compose.yaml` (PostgreSQL). **Без триггеров** в БД.
* Все версии зависимостей — через `<properties>` в `pom.xml`.
* Слои: client/domain/api/persistence. **Маппинг только через domain**.
* Канонические таймфреймы — в YAML (canonical → per-exchange mapping). **Только закрытые свечи**. `coverage_end_utc` — учесть.
* Стиль: одна переменная на строку; `{}` после `if`; аннотации **над** полями; строки → `Constants.*`; конечные значения → `enum`.
* Коды ошибок (dot-нотация) и исключения: `ServiceException`, `UnexpectedException`.
* Проверки: `Objects.isNull/nonNull`, `Objects.equals`, `BooleanUtils.isFalse`, `CollectionUtils.isEmpty/isNotEmpty`.
* В миграциях — `COMMENT ON TABLE/COLUMN` **на всё**.

## Что реализовать

### M4 — Загрузка истории свечей

1. **HistoryService**

   * Методы:

     * `downloadAll(exchangeInstrumentId, timeframes: List)` — первичное заполнение по всем ТФ (от старших к младшим).
     * `downloadIncremental(exchangeInstrumentId, timeframe)` — докачка от последней сохранённой свечи.
     * `refillRange(exchangeInstrumentId, timeframe, fromUtc, toUtc)` — целевая докачка диапазона (используется M5).
   * Правила:

     * Только **закрытые свечи**; UTC; append-only (`ON CONFLICT DO NOTHING`) с уникальным ключом `(exchange_instrument_id, timeframe_canonical, ts_utc)`.
     * Один писатель на серию `(exchange_instrument × timeframe)`.
     * Пагинация/батчи и задержки по конфигу (rate-limit/timeout/retry). Ошибки — `ServiceException(Constants.Errors.REMOTE_TIMEOUT)` и т.п.
     * После успешной вставки — обновить coverage (`coverage_start_utc`, `coverage_end_utc`) для серии.
2. **Конфигурация (`application.yaml`)**

   ```yaml
   app:
     history:
       batchLimit: 200
       requestTimeoutMs: 10000
       maxRetries: 3
       retryBackoffMs: 500
       pageDelayMs: 250
       rateLimitPerSecond: 4
   ```
3. **REST-эндпоинты**

   * `POST /api/history/fill` — первичное заполнение: `exchangeInstrumentId`, `timeframes[]?`
   * `POST /api/history/fill/incremental` — докачка по серии.
   * `POST /api/history/fill/range` — целевая докачка диапазона (для M5).
   * `GET  /api/coverage` — вернуть coverage по сериям.
   * Эндпоинты описать в Swagger.
4. **Metrics/Логи**

   * Счётчики: `history.candles.inserted`, `history.calls`, `history.retries`, `history.rate_limited`.
   * Гейдж: `history.lag.bars` (оценка отставания).

### M5 — Целостность и докачка данных

1. **ConsistencyService**

   * `scan(exchangeInstrumentId, timeframe, windowBars)` — проверка:

     * Шаг сетки по ТФ, дубли, «дыры» (ts пропуски).
   * `gapFill(exchangeInstrumentId, timeframe, gaps[])` — таргетированная докачка через `HistoryService.refillRange(...)`.
   * После операций — пересчитать coverage.
   * Политика: идемпотентные вставки; журналировать найденные/закрытые «дыры» (лог/метрики).
2. **Конфигурация (`application.yaml`)**

   ```yaml
   app:
     consistency:
       scanWindowBars: 5000
       refillChunkBars: 1000
   ```
3. **REST-эндпоинты**

   * `POST /api/consistency/scan` — вернуть отчёт по сетке/дырам.
   * `POST /api/consistency/fill-missing` — принять список пропусков и инициировать докачку.
4. **Metrics**

   * `consistency.gaps.found`, `consistency.gaps.filled`, `consistency.scans.total`.

## Требования к БД/миграциям

* Если потребуются новые индексы/таблицы для coverage/истории — добавить миграции SQL **без триггеров** и с полными `COMMENT ON TABLE/COLUMN`.
* Убедиться, что уникальные ключи и индексы соответствуют требованиям M4–M5.
